# AI Usage Declaration

**Tool:** Claude (Anthropic), used throughout the assignment as a pair programmer and reviewer.

## How it was used

**Design discussion.** For each part, we discussed the requirements and the alternatives before writing code: how to interpret `clientId` and `urlId`, which status code each failure gets, why unknown and disabled operations return the same 404, how to tell a timeout from caller cancellation, the header allowlist, the audit policy when the database is down, and how optimistic concurrency works with `rowversion`. I made the decisions; they are documented in DESIGN-NOTES.md.

**Code I wrote, with AI review and corrections.** I wrote the first version, the AI pointed out defects, and in many places it corrected them directly and explained the fix. I reviewed each change.
- `PayloadDecryptor`, `ProxyDbContext` (including automatic timestamps) and the development seed.
- `ProxyService`: the pipeline, parameter validation, the encryption policy, the size check, the audit wrapper (`ExecuteAsync` with `finally`), and the mapping of upstream outcomes.
- `HttpUpstreamForwarder` (first version, including the timeout and cancellation handling), `ConfigurationKeyProvider` and `ProxyController`.
- The header allowlist plumbing: `ProxySettings`, its registration, and passing incoming headers from the controller to the service.
- Most of the `ProxyServiceTests` (requirements 1-12, 14 and 17).

**Code generated by AI and reviewed by me.**
- Entity classes, EF Core entity configurations, DTOs, error code constants, and the repository and application interfaces.
- URL building in `ProxyService`, and the final version of the header filter.
- The bounded response reading loop in `HttpUpstreamForwarder`.
- The configuration update endpoint: `OperationAdminStore` and `AdminController`.
- Test infrastructure: the fakes (`RecordingForwarder`, `FakeOperationRepository`, `FakeAuditor`) and `StubHttpMessageHandler`.
- `HttpUpstreamForwarderTests`, most of `PayloadDecryptorTests`, and the Testcontainers fixture and `OperationAdminStoreTests`.

For each of these, we went over what the code does and why before I committed it.

**Documentation.** The AI drafted README.md and DESIGN-NOTES.md from the decision log we kept during development. I reviewed and edited them.

**Testing and verification.** I ran all tests locally and tested the API manually through Swagger against JSONPlaceholder (valid requests, rejections, an oversized response, and two concurrent admin updates), and checked the audit rows in SQL Server. Manual testing found one defect the tests had missed (a stale version with unchanged values returned 200), which was then fixed and covered by a test.

I can explain, defend and modify any part of the submitted code.
